
**全库搜索 `.pdf` / `.png` / `.jpg` 的消费方 —— 除了上面那行注释，零命中。**

也就是说：用户可以上传药品说明书照片、供应商报价单 PDF、药检报告扫描件，文件会老老实实躺在 `data/session/<tid>/` 里，然后**没有任何 Agent 知道它存在**。

这个判断直接决定了下面方案的排序：**优先级最高的不是"引入一个新模态"，而是"把这条已经修到一半的路修通"。** 前者是加分项，后者是补一个已经许诺给用户却没实现的功能。

（顺便：`/files/upload` 目前因为 `content` 未定义必然 500，所以严格说这条路连第一步都没通。见评审 §1.1。）

## 方案一：报告图表化（数据 → 图）—— 输出侧多模态

### 做什么

给主 Agent 加一个 `render_chart` 工具：拿 SQL 查询结果（已经在 `/scratch` 里了）→ matplotlib / pyecharts 画图 → PNG 落到 `data/session/<tid>/` → `generate_markdown` 在报告里用相对路径引用。

```python
@tool
async def render_chart(
    scratch_path: str,          # ← 关键：只接受 /scratch 里的数据文件路径
    chart_type: Literal["line", "bar", "grouped_bar", "pie"],
    x_column: str,
    y_columns: list[str],
    title: str,
    runtime: ToolRuntime,
) -> str:
    """把已落盘的 SQL 结果画成图表，返回可在报告中引用的文件名。

    数据只能来自 /scratch 下的 CSV —— 不接受模型直接传数值，
    从根上杜绝"图里的数字是模型编的"。
    """
```

### 为什么这条应该第一个做

**1. 它是唯一一个零幻觉风险的多模态方向。**
所有其他方案都是"模型理解模态"（图 → 文本，有幻觉），只有这个是"代码渲染模态"（数据 → 图，确定性变换）。图是从 CSV 直接画出来的，不经过模型，**不可能出现"图里的数字和数据库不一致"**。

**2. 它顺手解决了评审 §2.2 的一部分。**
签名里我刻意写成 `scratch_path` 而不是 `data: list[dict]`。这一个设计选择把"图表数据必须来自真实查询结果"变成了**类型层面的强制**，而不是 prompt 里的一句叮嘱。这正是你自己在 `rag_tools.py` 注释里总结的那条原则：

> *"凡是能用一行 if 写死的约束，就不该交给模型去权衡。"*

**3. 你的业务场景在喊着要图。**
README 的示例查询是「分析布洛芬采购价格趋势」，`prompts.yml` 要求报告"不少于 1000 字"。价格趋势、库存周转、销量对比——**全都是时间序列和分类对比，天生该用图表达**。现在用 1000 字文字描述一条折线，是把最适合视觉的信息强行塞进最不适合的通道。

**4. 成本几乎为零。** 不调任何模型。纯 CPU 渲染，几十毫秒。

**5. 演示效果与投入之比最高。** 一份带三张图的分析报告，和一份纯文字报告，给人的观感差距是数量级的。而工程量大约 1–2 天。

### 风险与坑

| 坑 | 说明 |
|---|---|
| **中文字体** | matplotlib 默认字体不含中文，图例会显示成方框。必须显式指定字体并把字体文件纳入部署（Docker 里尤其容易漏） |
| **前端渲染不了相对路径图片** | `web/app.py:667` 是 `st.markdown(text)` 渲染报告，markdown 里的 `![](chart.png)` Streamlit 解析不了服务端相对路径；而 `/files/content` 的白名单只有 `{.md,.txt,.csv,.json}`，图片取不到。需要：`/files/content` 前把 markdown 里的图片路径重写成 `/files/download?...` 的绝对 URL，或前端解析后用 `st.image` 单独渲染 |
| **图表类型选择交给模型** | 模型可能给时间序列选饼图。可以在工具内加校验（x 轴是日期就拒绝 pie），或干脆由代码根据数据形状推断 |
| **别忘了 dataviz 规范** | 配色、坐标轴、图例这些如果随手写，图会很难看，反而拉低观感。值得花半天定一套统一的图表样式 |

### 评分

| 维度 | 分数 | 说明 |
|---|:--:|---|
| 业务价值 | 8 | 直接提升交付物质量，用户第一眼就能感知 |
| 工程量（越高越省） | 9 | 1–2 天，不碰 Agent 循环，不碰安全模型 |
| 风险 | 9 | 确定性变换，零幻觉；最大的坑只是中文字体 |
| 架构契合度 | 9 | 复用 `/scratch`（L0）→ `session_dir`（L2）的现有分层，一行都不用改 |
| 简历/演示含金量 | 7 | 不算前沿技术，但"用类型签名强制数据可溯源"这个设计点很能讲 |
| **总分** | **8.5** | **建议第一个做** |

## 方案二：药品图像与说明书理解（图 → 结构化）—— 输入侧多模态

### 做什么

新增第四个子 Agent `document-intake`，工具是 `analyze_image(path, question)`，底层调 DashScope 的视觉模型（`qwen-vl-max` / `qwen3-vl` 系列，具体 model id 以百炼控制台为准）。

链路：

```
用户上传药品包装照片 / 说明书扫描件
  → /files/upload 落到 session_dir
  → 主 Agent 派 document-intake
  → analyze_image 抽结构化字段：
       药品名 / 规格 / 批号 / 有效期 / 生产厂家 / 存储条件 / 禁忌
  → 关键字段走 HITL 人工确认   ← 这里是本方案的架构亮点
  → 确认后：写入 /scratch 供分析，或 upsert 进 ChromaDB 知识库
```

### 为什么这条价值最高

**1. 它接上了那条断掉的链路。** 见 §0。你已经许诺了图片上传能力，也预留了 PDF 扩展点，还建了空的 `app/infra/pdf/` 模块 —— 这个方案是把已有的三处伏笔一次性兑现。

**2. 医药行业的真实输入本来就是非结构化的。** 说明书、包装盒、药检报告、冷链温度记录单、供应商传真报价——**大部分从来不是 CSV**。一个"医药深度搜索系统"如果只能读数据库和网页，它处理的是这个行业信息的一小半。

**3. 最关键的一点：你已经有 HITL 基础设施了。**

这是我认为这个方案真正优雅的地方。VL 抽取的最大问题是**数字和批号容易读错**（`0`/`O`、`8`/`B`、小数点位置），而药品有效期读错一位是安全事故。所以 VL 抽取**必须有人确认**。

而"高风险操作暂停等人确认"——你为 SQL 已经建好了一整套：`interrupt()` 抛出 → `_serialize_interrupt` 摊平 → WebSocket 推 `interrupt` 事件 → 前端审批卡片 → `POST /decision` → `Command(resume=...)` 恢复。包括多中断并发时按 id 逐个恢复的那个坑，你都踩过并解决了。

**VL 字段确认和 SQL 审批是同一个抽象**：暂停 → 展示 → 人类 approve/edit/reject → 恢复。`edit` 分支甚至天然对应"人工修正读错的批号"。

配置项也已经是通用的：

```python
hitl_interrupt_tools: list[str] = ["execute_sql_query"]   # ← 是个 list，为扩展留的
```

**但要注意一个实现细节**：目前 interrupt 的判定逻辑是**绑死在 `database_query.py` 的 router 里**的（`make_router` → `assess_sql_risk` → `approve_sql` 节点），不是一个通用中间件。所以要复用，得先把这套"风险评估 → 审批节点 → 路由"从 db 子图里抽成可复用的组件（或者直接用 LangChain 的 `HumanInTheLoopMiddleware`，挂在 document-intake 子 Agent 上）。**这个重构本身就是这个方案最有价值的部分** —— 它把你的 HITL 从"SQL 专用"变成"任意高风险工具通用"。

**4. 复用降级模式。** VL 模型不可用时怎么办？你在 `knowledge_base.py` 里已经有答案了 —— `_build_degraded_tools()` 返回一个"知识库当前不可用，请改用网络搜索"的假工具。这套模式直接抄过来：VL 挂了就返回"图像识别不可用，请手工录入关键信息"，Agent 链路不崩。

### 风险与坑

| 坑 | 说明 |
|---|---|
| **图像进上下文是 token 黑洞** | 一张 1024×1024 图约 1000+ token，而且**不可摘要、不可裁剪**（见下面 §5.1 的详细分析）。铁律：**图片只给 VL 子 Agent 看，永不进主 Agent 上下文**，主 Agent 只收文本抽取结果 + 路径 |
| **预算中间件会失准** | `price_per_1m_input` 是单一价格，VL 的图像 token 计价规则不同；加上评审 §2.1 说的"子 Agent 不计预算"，成本会双重失控 |
| **幻觉在这里是安全问题** | 普通场景读错数字是瑕疵，药品有效期读错是事故。**必须 HITL，不能配置成可关闭** |
| **`_offload.py` 只吃 str** | `offload_if_large(text: str)` 处理不了二进制。图片走独立的存储路径，不要硬塞进现有卸载机制 |
| **中文竖排 / 印章 / 反光** | 真实药盒照片有曲面、反光、压印文字，识别率会明显低于 demo 里的清晰扫描件。要有"识别置信度低就直接请人工录入"的兜底 |

### 评分

| 维度 | 分数 | 说明 |
|---|:--:|---|
| 业务价值 | 9 | 补上行业最主要的非结构化输入通道 |
| 工程量（越高越省） | 6 | 3–5 天，且需要先把 HITL 从 db 子图里抽出来 |
| 风险 | 6 | 幻觉是安全问题；上下文与预算两处需要专门设计 |
| 架构契合度 | 10 | 复用 HITL、复用降级模式、兑现三处已有伏笔 —— 契合度是所有方案里最高的 |
| 简历/演示含金量 | 9 | "把 SQL 专用的 HITL 抽象成通用的高风险工具审批层，然后用它兜住 VL 的幻觉" —— 这是一个真正有架构含量的故事 |
| **总分** | **9.0** | **天花板最高，建议第二个做（在方案一之后）** |

## 方案三：报价单 / 药检报告的版面结构化（文档 → 数据库新数据源）

### 做什么

方案二的"业务纵深版"。不止是读懂一张图，而是把**结构化文档变成数据库里的新表**：

```
供应商报价单（PDF / 扫描件 / Excel）
  → 版面理解 + 表格抽取
  → 结构化成 quotes 表：{supplier, drug_name, spec, unit_price, valid_until, moq}
  → 人工确认
  → 写入 MySQL（或先落 staging 表）
  → 现有的 database-query 子 Agent 立刻就能分析它
```

关键句：**这不是"加一个模态"，而是"给现有的 SQL 分析能力喂一个新数据源"。**

### 为什么这条业务价值最高

**1. 它是唯一能产生 1+1>2 的方向。**
其他方案都是在现有能力旁边并列加一项。这个方案是把新输入接进**你已经建好的最强能力**——SQL 分析 + 多表聚合。一旦报价单进了库，立刻能回答：

- "这家供应商这次的报价，比我们过去 12 个月的采购均价高多少？"
- "同规格的布洛芬，三家供应商谁最便宜，考虑 MOQ 后的实际单价呢？"
- "有哪些在报的品种，我们库存还够 3 个月以上？"（报价单 × inventory 联查）

这些问题现在**一个都答不了**，因为报价单在邮箱里躺着。而答案所需的分析能力你**已经全部具备**了——包括 `prompts.yml` 里那段写得很好的"多表聚合笛卡尔积"硬规则。

**2. 它是真实的痛点。** 医药采购的日常就是对着几份格式各异的报价单手工比价。这是那种"演示的时候采购部同事会真的凑过来看"的功能。

### 风险与坑

| 坑 | 说明 |
|---|---|
| **写库打破了"只读"的核心假设** | 你整个安全模型建立在 `assert_read_only` 之上，MySQL 连接被设计成只读。要写入就得开一条**独立的、权限隔离的写通道**（不同的 DB user、只能写 staging 表），绝不能放宽现有那条只读路径。这是本方案最大的架构冲击 |
| **表格版面是老大难** | 合并单元格、跨页表格、手写批注、双栏排版——识别率在真实样本上会比预期低不少 |
| **错一个小数点 = 采购决策错** | 必须有"入库前逐行人工核对"的界面，不能只是弹一个确认框 |
| **工程量最大** | 1–2 周，还要设计 staging → 审核 → 正式表的数据流转 |

### 评分

| 维度 | 分数 | 说明 |
|---|:--:|---|
| 业务价值 | 10 | 唯一能和现有 SQL 能力产生乘法效应的方向 |
| 工程量（越高越省） | 4 | 1–2 周；要新建写通道、staging 表、人工核对界面 |
| 风险 | 5 | 打破只读假设；表格识别在真实样本上不稳定 |
| 架构契合度 | 7 | 复用 SQL 分析能力（+），但冲击只读安全模型（−） |
| 简历/演示含金量 | 9 | "把非结构化输入变成可 SQL 分析的结构化数据"是很硬的业务价值叙事 |
| **总分** | **8.0** | **业务上限最高，但建议放到第三步——等方案二把 VL 和 HITL 的基础打好** |

## 方案四：跨模态 RAG（图文同空间检索）

### 做什么

把 `OpenAIEmbedder` 换成多模态嵌入（DashScope `multimodal-embedding-v1` 之类），让图片和文本嵌到同一向量空间。之后文本查询"胰岛素怎么存"可以召回冷藏柜的示意图、药品外观图、图示化的操作规范。

### 为什么技术上很优雅

**这是你的 Protocol 抽象真正付费的时刻。**

```python
# app/rag/store.py —— store 只认 embeddings，不认谁生成的
async def add(self, ids, texts, embeddings, metadatas): ...

# app/rag/embedder.py —— Embedder 是 Protocol
@runtime_checkable
class Embedder(Protocol):
    async def embed(self, text: list[str]): ...
```

`ChromaStore` 和 `ingest_documents` **都不认识 `OpenAIEmbedder`**，只认 Protocol。换成多模态 embedder，`store.py` 一行不用改。你在 `ingest.py` 注释里写的那句"这就是 Protocol 的价值——这个函数不认识具体实现，只认合同"，在这里会得到验证。

### 但为什么分数不高

**1. 你没有图片语料。**

```
knowledge_base/
├── 布洛芬.md          938 B
├── 阿莫西林.md       1001 B
└── 冷藏药品管理规范.md 1353 B
```

三个纯文本 md 文件，总共 3.3KB，**零张图片**。跨模态检索的价值完全取决于图片语料的规模和质量。**没有语料，这个方案的实际收益是零**——它只是让架构"支持"了一件不会发生的事。

**2. 分数阈值的语义会失效。**

```python
_DEFAULT_SCORE_THRESHOLD = 0.4   # score = 1/(1+distance)，注释说 0.4 ≈ distance 1.5
```

这个阈值是针对**文本-文本**的 distance 分布调出来的（注释里也诚实写了"需要根据实际效果调，不是理论最优值"）。图文跨模态的 distance 分布完全不同，通常图文相似度整体偏低。混在一个 collection 里做统一 top_k 检索，结果会是**图片几乎永远进不了前 5，或者反过来图片挤掉了更相关的文本**。

正确做法是图文**分桶检索再融合**（各取 top_k，分别用各自的阈值，最后按类型配额合并），而不是简单换个 embedder。这个工作量比"换 embedder"大得多。

**3. 依赖前置。** 图片语料从哪来？——从方案二/三的入库链路来。**所以这个方案天然应该排在方案二之后**，它是方案二的下游收益，不是独立选项。

### 评分

| 维度 | 分数 | 说明 |
|---|:--:|---|
| 业务价值 | 5 | 没有图片语料时收益为零；有了之后才谈得上 |
| 工程量（越高越省） | 6 | 换 embedder 很轻，但分桶检索 + 阈值重调不轻 |
| 风险 | 6 | 中文医药领域跨模态召回质量存疑；现有阈值语义失效 |
| 架构契合度 | 8 | Protocol 抽象让替换成本极低（这一点确实漂亮） |
| 简历/演示含金量 | 7 | "Protocol 抽象让多模态嵌入零成本替换"是个好论点 |
| **总分** | **6.5** | **不是独立方案，是方案二的下游。等有了图片语料再做** |

## 方案五（不推荐）：语音输入 / 语音播报

### 评估

ASR 把语音转成 query，TTS 把报告读出来。技术上最容易接（DashScope 有现成接口），一天能跑通。

**但它和你的产品定位是错配的。**

你做的是"深度搜索 + 分析报告"。报告的特征是：长（要求 1000 字以上）、结构化（多级标题、表格）、需要反复对照数字。**这类内容没人会用耳朵听** —— 听完第三段就忘了第一段的数字，而且无法回看。语音适合的是短指令和短反馈，不是深度分析。

输入侧稍微好一点（"帮我查一下布洛芬的库存"确实适合说出来），但收益也只是省几秒打字。

有一个**窄场景**确实成立：仓库/药房人员戴着手套、手上拿着药盒时，语音查询比打字方便。但这需要移动端 + 现场部署，是另一个产品，不是给你现在这个 Streamlit 后台加个麦克风图标。

**这是典型的"简历填充型"多模态**——能写进技术栈列表，但被问"为什么要加这个"的时候答不上来。而在面试里，一个答不上"为什么"的技术点是**负分**，不是零分。

| 维度 | 分数 |
|---|:--:|
| 业务价值 | 3 |
| 工程量（越高越省） | 9 |
| 风险 | 8 |
| 架构契合度 | 4 |
| 简历/演示含金量 | 2 |
| **总分** | **4.0 —— 不建议做** |

## 方案六（不推荐现阶段）：VL 读网页图表

### 评估

Tavily 返回文本，但医药行业报告的关键数据常常只在图里（市场规模柱状图、份额饼图）。思路是：浏览器截图 → VL 读图 → 提取数据点。

**三个理由说明现在不该做：**

1. **链路太长**：要引入浏览器自动化（截图）、页面滚动定位、图表区域裁剪。每一环都会失败，而且失败是静默的。
2. **这是 VL 最不可靠的任务**：读柱状图的具体数值需要精确的坐标-刻度映射，模型在这件事上的错误率远高于读文字。它会给你一个**看起来很合理但是错的**数字。
3. **和你自己的原则直接冲突**：你的 prompt 里写着"凡是要写进报告的数字，必须 read_file 读回原文核对""禁止编造来源"。VL 从图里读出来的数字**没有可核对的原文**——它就是模型的一个推测。把这种数字写进医药分析报告，正是你花了大量 prompt 篇幅在防的事情。

如果确实需要图里的数据，更稳的路是找该报告的原始数据源（数据表、财报附注），而不是让模型看图猜。

| 维度 | 分数 |
|---|:--:|
| 业务价值 | 6 |
| 工程量（越高越省） | 3 |
| 风险 | 2 |
| 架构契合度 | 3 |
| 简历/演示含金量 | 6 |
| **总分** | **5.0 —— 不建议现阶段做** |

## 5. 无论选哪个方案，这四处现有设计会被打破

这一节比上面的方案排序更重要。多模态不是"多一个工具"那么简单，它会同时打破你系统里四个正在正常工作的机制。**提前设计，不要等出问题再补。**

### 5.1 三层上下文管理对图像**全部失效**

你的三层策略是：

```
L0 卸载 (>4KB 落盘)  →  L1 摘要 (>60K LLM 压缩)  →  L2 裁剪 (>80K 机械清除)
```

逐层看它们对图像做什么：

| 层 | 对文本 | 对图像 |
|---|---|---|
| L0 `offload_if_large` | 落盘，回摘要 + 路径 | **签名是 `text: str`，二进制根本进不来** |
| L1 `SummarizationMiddleware` | LLM 压缩，保语义 | **无法摘要图片**（摘要模型是 `qwen-turbo`，纯文本） |
| L2 `ContextEditingMiddleware` | 机械丢弃旧工具结果 | **丢掉图片 = 丢掉唯一的证据**，且丢之前无法评估价值 |

一张 1024×1024 的图约 1000+ token，几张图就能占掉上下文的可观比例，而**三层机制一层都管不住它**。

**铁律（建议写进 `docs/context_strategy.md`）：**

> 图像永不进入主 Agent 上下文。只有 VL 子 Agent 看到图像本体；主 Agent 只收到文本抽取结果 + 图像路径。需要复核时，主 Agent 派 VL 子 Agent 带着具体问题再看一次。

好消息是：**这和你已有的 L0/L2 分层是同构的**。你已经建立了"大块原始资料留在 L0，只把摘要给上下文"的模式，图像只是这个模式的一个新品类 —— 叫它"L0 图像层"，规则完全一样，只是存储从 state 通道换成真实文件。

### 5.2 预算中间件会失准，而且是双重失准

```python
price_per_1m_input: float = 0.5     # 单一输入价格
price_per_1m_output: float = 2.0
```

- **第一重**：VL 的图像 token 计价规则和文本不同，用单一 `price_per_1m_input` 算出来的成本是错的。
- **第二重**：评审 §2.1 已经说过，`BudgetMiddleware` 只包主 Agent，子 Agent 不计。而 VL 调用**恰好全部发生在子 Agent 里**——也就是说加了多模态之后，**最贵的那部分调用刚好是完全不被统计的那部分**。

`budget_max_cost_usd = 1.0` 会从"偏低估"变成"基本没意义"。

**建议**：做多模态之前，先把评审 P1 里的"预算计数器跨图共享"做掉。顺序不能反 —— 否则你是在一个不会报警的系统上接一个更贵的模态。

### 5.3 `generate_markdown` 的交付链路不支持图片

三个环节都得改：

1. **工具本身**：`generate_markdown(content, filename, topic, summary)` 只写单个 `.md`。带图报告是一个"md + 若干 png"的资产组合，`record_report` 的索引结构（单个 `path` 字段）也只记了一个文件。
2. **`/files/content`**：白名单是 `{.md, .txt, .csv, .json}`，图片取不到（只能走 `/download`）。
3. **前端**：`web/app.py:667` 是 `st.markdown(text)`，markdown 里的相对图片路径 Streamlit 解析不了。

**最小改法**：`/files/content` 返回前，把 markdown 里的 `![](chart.png)` 重写成 `![](绝对URL/files/download?thread_id=...&filename=chart.png)`。一个正则替换搞定，前端零改动。

### 5.4 RAG ingest 的 `_load_file` 签名不够用

```python
def _load_file(path: Path) -> str | None:      # ← 返回单个字符串
```

你留的扩展点是 `elif suffix == ".pdf": return _load_pdf(path)`，但**这个签名接不住 PDF**：一个 PDF 页面里同时有正文、表格、插图，返回单个字符串就意味着丢掉后两者。

建议在动手前先把签名改成返回结构化的块列表：

```python
@dataclass
class DocBlock:
    kind: Literal["text", "table", "image"]
    text: str | None          # text/table 的内容，或 image 的 VL 描述
    image_path: Path | None   # image 块指向真实文件
    page: int | None

def _load_file(path: Path) -> list[DocBlock]: ...
```

改签名是个小重构，但**在加 PDF 之前改，比加完之后改便宜十倍** —— 现在只有 md/txt 两个分支，改动面极小。

### 建议的执行顺序

**第 0 步（前置，不做多模态也该做）**
把评审里的 P0 修完 + 预算计数器跨图共享（§5.2）。理由：`/files/upload` 现在是 500，多模态的第一步就走不通；预算不修就是在没有刹车的车上加马力。

**第 1 步：方案一（报告图表化）** — 1～2 天
零风险、不碰 Agent 循环、立刻改善交付物观感。顺便把 §5.3 的图片交付链路打通 —— **这条链路是方案二和三的共同前置**，在这里用最简单的场景先跑通它，后面就白赚。

**第 2 步：方案二（图像理解）** — 3～5 天
先做架构准备：把 HITL 从 `database_query.py` 的 router 里抽成通用组件（或换用 `HumanInTheLoopMiddleware`），确立"图像不进主上下文"的铁律（§5.1），改 `_load_file` 签名（§5.4）。然后接 VL。

**第 3 步：方案三（报价单结构化）** — 1～2 周
此时 VL、HITL 通用化、图片交付链路都已就绪，剩下的是业务纵深：写通道隔离 + staging 表 + 人工核对界面。

**第 4 步：方案四（跨模态 RAG）** — 视语料而定
等方案二/三真的往知识库里存进了几百张图，再谈跨模态检索。届时 Protocol 抽象会让 embedder 替换非常轻，但要单独做图文分桶检索。

### 如果只做一件事

**做方案一。** 理由：1～2 天、零幻觉风险、立刻可见、且顺手打通方案二/三都要用的图片交付链路。它是唯一一个"即使后面不继续做多模态，也不会浪费"的选项。

### 如果是为了讲一个完整的技术故事

**做方案二，但把重点放在 HITL 通用化上。**

值得讲的不是"我接了个 VL 模型"（谁都能接），而是：

> "VL 抽取药品有效期会读错，而药品有效期不能错。我没有靠调 prompt 让模型更小心 —— 我把原本为 SQL 建的那套 `interrupt` 审批机制抽象成了通用的高风险工具审批层，让 VL 的输出必须经人确认才能入库。同一套 approve/edit/reject，`edit` 分支正好用来修正读错的批号。"

这个故事里有：对模型能力边界的判断、对现有资产的复用、把概率性约束换成确定性流程。**比任何模态清单都有说服力。**
