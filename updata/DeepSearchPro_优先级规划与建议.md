# DeepSearch Pro：多模态 + 测评 落地前的架构优先级规划

> 依据：`updata/DeepSearchPro_架构评审_2.md`、`updata/DeepSearchPro_多模态融合方案.md`、`docs/architecture.md`、`docs/context_strategy.md`、`README.md`。
> 视角：在你已有的两份评审结论之上，把"多模态"和"测评"这两条新工作线，插进现有的修复计划里，给出一条唯一的执行顺序。
> 日期：2026-08-16

---

## 0. 结论先行

**不要把"多模态"和"测评"当成两个新项目并行推进，它们必须排在架构评审的 P0/P1 之后，而且测评要比多模态先有雏形——原因很简单：你现在没有任何机制能判断"加了多模态之后，系统是变好了还是变差了"。**

三条线的依赖关系是单向的：

```
架构修复(P0止血 → P1护栏/安全)  →  测评雏形(能跑、能打分)  →  多模态(方案一→二→三→四)
                                        ↑
                              两条线共用同一套回归验证
```

- **架构修复必须最先做**：`/files/upload` 现在 100% 抛异常，多模态的第一步（上传图片）连门都进不去；预算护栏对子 Agent 完全失效，多模态最贵的调用（VL）恰好全部发生在子 Agent 里——不修，你是在一辆没有刹车的车上加马力。这是两份评审文档都独立得出的结论，不是我重复强调。
- **测评要插在多模态之前，而不是之后**：你现有的"引用落地性"约束（§2.2 grounding）目前是 prompt 里的一句叮嘱，没有代码校验；多模态一旦引入 VL，幻觉的后果从"报告数字有瑕疵"升级为"药品有效期读错=安全事故"。**没有测评手段，你没法证明 HITL 真的拦住了错误，也没法在后续改动时确认没有引入新的幻觉。** 测评不是加分项，是多模态方案二（图像理解）能不能安全上线的前提条件。
- **这不意味着测评要建一整套体系再动手**——下面第 4 节给出一个"够用就行"的最小测评雏形，工程量和方案一（报告图表化）相当，可以并行推进。

## 1. 综合优先级排期表

把架构评审的 P0–P3、多模态方案的步骤 0–4、以及新增的测评线，合并成一条时间线。**同一优先级内的任务可以并行，跨优先级不建议提前做**（原因见每条后面的说明）。

### P0（半天～1天）：止血，三条线共同的前提

| # | 任务 | 来源 | 为什么必须现在做 |
|---|---|---|---|
| 1 | 修 `routes_files.py:165` 的 `content` NameError | 架构评审 §1.1 | `/files/upload` 现在必现 500——多模态和测评都需要先能上传文件 |
| 2 | 修 `TaskService._evict()` 反向条件 | 架构评审 §1.2 | 任务并发时相互清除记录，测评跑批量用例时这个 bug 会直接让结果不可信 |
| 3 | `EventBus.publish` 改 `for q in list(queue)` | 架构评审 §1.3 | 前端刷新即可触发，测评需要稳定的事件流来判断任务是否正常完成 |
| 4 | 依赖收进 `pyproject.toml` 并锁版本 | 架构评审 §5.1 | 硬伤：clone 下来装不起来，任何后续工作的地基 |
| 5 | GitHub Actions：`ruff check` + `pytest` | 架构评审 §5.2 | 后面每条线都会不断改代码，没有 CI 意味着回归全靠肉眼 |

**不建议在这一步就开始碰多模态或测评代码**——上面 5 条都是"跑起来就错"级别的问题，边修边加新功能只会让排查更难。

### P2（1周）：把想法落地成代码 + 方案一（报告图表化）

| # | 任务 | 来源 |
|---|---|---|
| 12 | grounding 校验节点（报告数字/URL 必须在 `/scratch` 原文中出现） | 架构评审 §2.2 |

| 15 | offload 换真实文件后端；checkpoint 加 TTL 回收 | 架构评审 §2.6 |
| 16 | 通用去重缓存装饰器，覆盖 `internet_search` | 架构评审 §2.8 |
| 17 | **方案一：报告图表化**（`render_chart` 工具） | 多模态评估 方案一 |
| 18 | **顺手打通图片交付链路**（`/files/content` 图片路径重写、前端渲染） | 多模态评估 §5.3 |

**为什么方案一排在这里、而不是更早**：它本身零风险（数据到图表是确定性变换，不经过模型），工程量小（1-2天），但它依赖的是"报告生成链路"，而这条链路正是第 12 条 grounding 校验要动的地方——放在同一批做，图表数据来源（`scratch_path` 强制）和 grounding 校验是同一个设计原则（"能用类型/代码约束的，不交给模型判断"），一起做效率更高。

**为什么 12（grounding）必须排在 17（图表）之前而不是之后**：图表化本身不需要 grounding 校验（它是确定性渲染），但**测评雏形要评估的第一个指标就是"报告里的数字是否有据可查"**——先有校验代码，测评才有东西可以断言。

**为什么方案二排在方案一之后、而不是并行**：方案二依赖方案一顺手打通的图片交付链路（§5.3），也依赖 P1 第 6 条修好的预算共享。更关键的是——**方案二引入的风险等级（药品有效期读错=安全事故）要求测评必须先能评估"HITL 是否真的拦住了错误"，而这只有在测评雏形（第 11 条）跑起来之后才谈得上**。

## 2. 明确"现在不能做"的清单

这几件事不是"优先级低"，是**在当前架构状态下做了会产生负收益或者建立在错误假设上**，建议明确排除，而不是模糊地"往后放"：

1. **语音输入/播报（多模态方案五）**——评估已经说得很清楚：产品形态是"1000 字以上结构化分析报告"，没人会用耳朵听长报告核对数字。这是"简历填充型"多模态，面试被问"为什么加这个"答不上来。**直接排除，不进任何排期。**

2. **VL 读网页图表（多模态方案六）**——和你自己在 prompt 里写的核心原则直接冲突："凡是要写进报告的数字必须能核对来源"，VL 读图猜出来的数字没有可核对的原文。**不建议现阶段做**，除非未来有明确的、只能靠图表获取数据的业务场景。

3. **跨模态 RAG（方案四）在没有图片语料之前不要做**——现在知识库是 3 个纯文本 md 文件，3.3KB。做了架构上"支持"了这件事，但收益是零，而且分数阈值（`_DEFAULT_SCORE_THRESHOLD=0.4`）是针对文本-文本调的，图文混检索会导致图片永远进不了 top_k 或反过来挤掉更相关的文本。**先有语料（来自方案二/三），再做。**

4. **在预算护栏跨图共享（P1 第 6 条）之前，不要接任何 VL 调用**——哪怕只是原型验证。两份文档都强调这一点：VL 调用发生在子 Agent，子 Agent 现在完全不计预算，"先跑起来看效果"这种试探方式，在这个系统里等于没有刹车地试探。

5. **在测评雏形跑起来之前，不要让方案二的 HITL 审批"演示性地"跳过**——很容易在早期原型阶段为了赶进度先把人工确认这一步简化掉，"反正是 demo"。但方案二的核心卖点就是"VL 输出必须经人确认"，跳过这一步等于放弃了这个方案唯一的架构亮点，而且一旦养成"demo 先跳过安全检查"的习惯，很容易忘记在正式版里补回来。

6. **报价单结构化（方案三）不要在方案二之前做**——它需要新开一条写库通道，这会打破全项目"只读"的核心安全假设（`assert_read_only`），是架构冲击最大的一步。必须等 VL 抽取和 HITL 通用化都跑稳，才有信心在"写"这条路径上复用同一套人工核对机制。

## 3. 为什么测评要单独拎出来讲

你的问题里提到"多模态和测评"，但现有的两份评审文档都没有覆盖测评——这不是遗漏，是因为测评这条线需要独立设计。以下是我的建议，基于当前架构状态给出。

### 3.1 现状：测评能力目前是 0

- `tests/` 下 20 个测试文件，覆盖的是**代码正确性**（config / db / hitl / rag / security / sql_guard 等单元与集成测试），这是工程测试，不是"回答质量"测评。
- 没有任何针对**端到端回答质量**的评测集：没有"给定 query，判断报告是否准确、是否有据可查、并行调度是否符合预期"这类测试。
- `verify_grounding`（架构评审 §2.2 建议的函数）目前只是设想，还没有实现——这正是测评能直接复用的第一块砖。

### 3.2 建议的测评雏形（对应上面排期表第 11 条）

**目标不是建一整套 LLM-as-judge 评测框架，是先有一个能跑、能给出确定性信号的最小闭环**，原则依然是你项目里反复出现的那句话："能用一行 if 写死的约束，就不该交给模型去权衡"——测评优先用确定性检查，LLM 判分放在第二位。

建议的最小雏形，按"确定性程度从高到低"分三层：

1. **确定性检查层（优先做，成本几乎为零）**
   - 复用架构评审 §2.2 建议的 `verify_grounding`：报告里的数字/URL 是否能在 `/scratch` 原文里找到。这既是护栏，也是测评指标——"未落地引用数"可以直接作为一个可追踪的分数。
   - SQL 安全回归：黑名单里的写操作、白名单外的表，跑一遍固定用例集，断言全部被拦截（这部分可以直接复用 `tests/` 里已有的 security 测试思路，只是换成"评测集"的形式持续跑）。
   - 并行度断言：给定几条已知有依赖关系的子任务 query，断言实际派发的并行/串行结构符合预期（这条等 P2 第 13 条"结构化计划"做完后价值最大，现在可以先用当前的 prompt 版本量出基线）。

2. **回归对比层（第二优先）**
   - 建一个 20～30 条的"金标准 query 集"（复用 README 里"分析布洛芬采购价格趋势"这类真实业务 query），每条记录：预期调用的子 Agent、预期涉及的表/数据源、报告应包含的关键结论。
   - 每次改动后跑一遍，对比报告的关键数字/结论是否漂移。这一层暂时可以是人工核对 + 脚本辅助比对，不需要一开始就上 LLM-as-judge。

3. **LLM 辅助评分层（最后再上）**
   - 用一个独立的评分模型（不是 qwen-max 本身，避免自己评自己）给报告的完整性、结构性打分。这一层价值最低、成本最高、且分数本身有主观性，建议排在最后，且只作为参考指标，不作为回归门槛。

### 3.3 测评为什么必须先覆盖"文本能力"再覆盖"多模态能力"

- 先在纯文本场景下把测评跑顺（P1 第 11 条），拿到一个稳定的基线分数。
- 加入方案一（图表化）后，重新跑一遍，因为它是确定性渲染，预期分数不应该下降——这本身就是对测评框架"是否敏感、是否稳定"的一次验证。
- 加入方案二（VL 图像理解）后，**新增一个专门的评测集**：给定一批已知正确答案的药品图片（批号、有效期人工核对过），跑 `analyze_image`，统计准确率和"低置信度正确转人工"的比例。这是方案二能否说"HITL 真的兜住了幻觉"的唯一证据来源。

## 4. 一句话版本

先花 3～4 天把架构评审的 P0/P1 修完（尤其是预算跨图共享和 HITL 绕过漏洞），同时搭一个只做确定性检查的测评雏形；然后做方案一（报告图表化，1-2天，零风险，顺手打通图片交付链路）；再做方案二（图像理解 + HITL 通用化，3-5天），做的同时把测评扩展到 VL 准确率评估；报价单结构化和跨模态 RAG 放到后面，语音输入和 VL 读网页图表直接排除。**测评不是多模态做完之后的验收环节，是多模态方案二能不能安全上线的前提条件，必须提前搭好骨架。**
